## Correction 1 — provider isolation must survive stale-cache fallback

Current `load_books_with_cancel` behavior:

1. computes a provider-sensitive cache signature;
2. normal cache load rejects signature mismatch;
3. if live catalog fetch fails, calls `try_load_cache(... allow_signature_mismatch = true)`.

Because the catalog cache is a single shared `calibre-books.toml`, that final fallback can return a stale catalog written by the *other provider*.

Example failure:

```text
legacy Calibre provider writes catalog cache
-> config switches to Caliberate
-> Caliberate service is unreachable
-> exact signature load misses
-> fetch fails
-> allow_signature_mismatch=true
-> legacy catalog is returned as if it were Caliberate
```

This violates Goal 0008 acceptance gate 11:

> Caliberate catalog/cache entries cannot collide with a legacy provider pointed at the same textual base URL.

### Required repair

Make stale/failure fallback provider-safe.

Acceptable solutions include:

- storing provider identity in `CachedBookList` and allowing stale-signature fallback only when provider matches; or
- provider-specific catalog cache files/directories; or
- another equally explicit provider partition.

Do **not** simply delete stale-cache fallback unless there is a concrete reason; offline/stale fallback is useful.

Secrets must remain absent from cache identity/payload.

### Required regression

Add a deterministic test that proves:

- legacy cache exists;
- current config is Caliberate with the same base URL;
- live Caliberate fetch fails;
- legacy cache is **not** returned.

Also prove same-provider stale fallback still works if that behavior is retained.
