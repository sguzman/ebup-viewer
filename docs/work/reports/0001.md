# Goal 0001 — Windows recovery and verified baseline

## Root Cause

The original `bindgen 0.59.2` failure was owned by `sonic-rs-sys 0.1.9`, which is a direct dependency of `lanternleaf-core` and is also reached through `piper-rs 0.1.9`. Its build script compiles a fixed Sonic C API and then unnecessarily invokes runtime bindgen for `sonic.h`. The project used the crates.io copy, so the prerequisite was not directly controlled by LanternLeaf.

After removing that dependency, a second independent blocker was proven as `bindgen 0.69.5 -> espeak-rs-sys 0.1.9 -> espeak-rs 0.1.9 -> piper-rs 0.1.9 -> lanternleaf`. The application uses only three eSpeak functions and five constants, so the vendored binding was reduced to that stable FFI surface and bindgen was removed there too. The dependency graph now contains neither bindgen nor clang-sys.

## Changes Made

- Vendored `sonic-rs-sys 0.1.9` and replaced its runtime bindgen step with checked-in Rust declarations for the stable C API used by LanternLeaf. The lockfile no longer contains `bindgen 0.59.2` or `peeking_take_while`.
- Removed espeak’s runtime bindgen step and added checked-in declarations for the exact FFI surface used by Piper.
- Added `.github/workflows/windows-baseline.yml`, which runs workspace check, build, test, and a native launch smoke on `windows-latest` (whose supported MSVC/CMake environment is now the only native build prerequisite). Repository-wide format checking is intentionally omitted because the existing tree has unrelated formatting drift.
- Updated three stale PDF pipeline test call sites to pass the current `PdfOcrNormalizationSummary` type.
- Moved the goal into `docs/work/active/` pending final blocked-state handoff.

## Remaining Blockers

The local Windows environment has no Visual Studio/MSVC C/C++ compiler (`where cl` found no compiler). LLVM-MinGW is installed, but it cannot safely substitute for the MSVC-target build: forcing it produces missing/incompatible CRT-header failures and would risk an ABI-mismatched binary. Local full-workspace check/build and native launch therefore remain unverified locally; the Windows CI job supplies the supported MSVC/CMake environment and verified check/build/process startup.

The package test suite has unrelated existing failures involving shared temporary-directory environment races, missing Pandoc, fixture calibration drift, PDF pipeline expectations, and abbreviation configuration. The Windows CI run reproduced 16 failures after check/build succeeded. Repairing those would broaden this baseline goal into feature/test redesign.

## Recommended Next Goal

Install the supported Visual Studio/MSVC C++ workload on the maintainer Windows environment and have the maintainer observe the clean-exiting native egui launch. Follow with a bounded test-fixture/environment stabilization goal before starting Windows TTS.
