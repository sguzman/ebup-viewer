# Goal 0004 — Windows TTS backend report

## Result

Implementation complete on `codex/0004-windows-tts-backend`. The required Windows build/test workflow was separated from the hosted renderer probe, and the native WinRT Windows speech backend now feeds the existing sentence-cache and shared Rodio/Sonic playback path.

## Windows Baseline

`.github/workflows/windows-baseline.yml` now runs check, build, and the full parallel `cargo test --workspace` in the required `native-workspace` job. The renderer probe is a dependent, separate capability job.

## Hosted Renderer Classification

The separate probe reports `renderer_supported` only when the app remains alive for the smoke interval. Known OpenGL/no-adapter failures are reported as `hosted_renderer_unavailable`; unexpected early exits fail the job. This preserves the known hosted graphics limitation without preventing build/test evidence.

## TTS Backend Architecture

`TtsEngine` now selects `TtsBackend::Piper` or `TtsBackend::Windows` for sentence preparation. Cache identity includes backend and model/voice identity plus normalized sentence text. Rodio output, WAV duration inspection, Sonic speed transformation, volume, pause, stop, and runtime cursor progression remain shared.

## Piper Compatibility

Piper remains the default and retains its worker-pool, model, eSpeak, and cache behavior. Existing Piper preparation/playback code remains in the shared engine.

## Windows Voice Catalog

The Windows-only module uses `SpeechSynthesizer::AllVoices`, exposes deterministic ID/display/language/gender descriptors, and supports refresh plus selectable voices in egui. A configured missing ID returns an actionable error; no configured ID uses the Windows default.

## Windows WAV Synthesis

The backend uses `SynthesizeTextToStreamAsync`, waits with the Windows future `join()` operation, verifies `audio/wav`, rejects empty/oversized streams, reads the stream into bytes, and atomically publishes a `.wav.partial` file as the cache WAV. The local Windows MSVC probe passed with three installed voices and produced a non-empty sentence WAV.

## Runtime and UI Wiring

Backend and voice ID are persisted in `AppConfig`, default to Piper/none for old configs, flow through reader settings and document loading, and are treated as TTS-affecting patches that cancel/rebuild from canonical reader state. egui exposes backend selection, voice ID, refresh, catalog selection, and error state without per-frame Windows calls.

## Tests

Added `crates/lanternleaf-core/tests/windows_tts.rs`, gated to Windows. It enumerates voices, records the count, skips synthesis only when the image has no usable voice, and otherwise synthesizes a fixed sentence and verifies non-empty output. The targeted Windows test passed locally on Windows: 1 passed, 3 voices.

Targeted Windows MSVC checks passed for `lanternleaf-core`, `lanternleaf-app`, and `lanternleaf-egui`; the Windows probe compiled and ran. Local core unit tests ran 168 tests with four pre-existing environment-dependent failures (two cache isolation/Pandoc setup cases); the new settings/config tests passed. The authoritative hosted workflow remains the acceptance evidence for the repository-wide test gate.

## CI

Authoritative hosted workflow run `34146382188` passed: `native-workspace` passed check/build/full parallel workspace tests, and `hosted-renderer-probe` passed with the truthful `hosted_renderer_unavailable` classification for the runner graphics limitation.
