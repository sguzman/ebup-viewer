# Goal 0001 — Windows recovery and verified baseline

## Root Cause

The original `bindgen 0.59.2` failure was owned by `sonic-rs-sys 0.1.9`, which is a direct dependency of `lanternleaf-core` and is also reached through `piper-rs 0.1.9`. Its build script compiles a fixed Sonic C API and then unnecessarily invokes runtime bindgen for `sonic.h`. The project used the crates.io copy, so the prerequisite was not directly controlled by LanternLeaf.

After removing that dependency, the next blocker was independently proven as `bindgen 0.69.5 -> espeak-rs-sys 0.1.9 -> espeak-rs 0.1.9 -> piper-rs 0.1.9 -> lanternleaf`. This bindgen invocation generates the broad espeak API used by Piper, so it remains a genuine libclang prerequisite.

## Changes Made

- Vendored `sonic-rs-sys 0.1.9` and replaced its runtime bindgen step with checked-in Rust declarations for the stable C API used by LanternLeaf. The lockfile no longer contains `bindgen 0.59.2` or `peeking_take_while`.
- Added standard Windows LLVM/libclang discovery to the vendored espeak build script. It honors explicit `LIBCLANG_PATH`, then checks `ProgramFiles\LLVM\bin`, `LLVM_INSTALL_DIR`, and PATH without hardcoding a user path.
- Added `.github/workflows/windows-baseline.yml`, which installs LLVM, exports `LIBCLANG_PATH`, then runs workspace check, build, format, and test gates on `windows-latest`.
- Updated three stale PDF pipeline test call sites to pass the current `PdfOcrNormalizationSummary` type.
- Moved the goal into `docs/work/active/` pending final blocked-state handoff.

- `cargo tree -i bindgen@0.59.2`: initially proved the Sonic ownership chain; after repair the package is absent.
- `cargo check -p sonic-rs-sys`: passed on Windows.
- `cargo test -p lanternleaf-core -p lanternleaf-app -p lanternleaf-egui`: compiled test binaries; `lanternleaf-app` passed 64 tests. The combined run reported 150 core tests passed and 17 existing failures.
- `cargo run -- --help`: attempted on Windows; failed before launch because `espeak-rs-sys` bindgen could not find `clang.dll`/`libclang.dll`.
- `cargo fmt --all -- --check`: failed on pre-existing formatting drift across unrelated files; no broad formatting rewrite was made.
- `git diff --check`: passed.

## Remaining Blockers

The local Windows environment has no LLVM/libclang installation. A `winget` attempt was throttled while downloading the 434 MiB LLVM installer, so the full workspace check/build/test and native launch gates could not be completed here. The source and CI now provide deterministic handling once LLVM is installed.

The package test suite also has unrelated existing failures involving shared temporary-directory environment races, missing Pandoc, fixture calibration drift, PDF pipeline expectations, and abbreviation configuration. Repairing those would broaden this baseline goal into feature/test redesign.

## Recommended Next Goal

Install LLVM/libclang on the maintainer Windows environment or run the new Windows CI gate, then rerun the complete workspace gates and perform the requested native egui launch verification. Follow with a bounded test-fixture/environment stabilization goal before starting Windows TTS.
